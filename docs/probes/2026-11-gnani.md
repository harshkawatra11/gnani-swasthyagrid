# Gnani.ai and LLM router contract probes, 8 Nov 2026

Run with `backend/scripts/probe_gnani.py` (and `--llm`) against the live Vachana API and
the configured LLM providers (about 10 calls: 4 TTS REST voices, 2 concurrent TTS REST,
1 TTS WebSocket turn of 2 sentences, 2 STT WebSocket sessions, 1 STT REST sanity check,
plus 1 Gemini tool-call round-trip and 3 `reasoning_effort` probes). Raw audio and event
output is under `backend/.runtime/probe/` (gitignored; not committed, per the project's
rule against committing audio fixtures with no transcript check). No key values appear
below or in any script output.

At probe time, `EVON_BASE_URL` was unset, so only Gemini answered the LLM probe. Evon
v3.3 itself was verified separately as a real, downloadable, Apache-2.0 model on
Hugging Face (`gnani/gnani-evon-v3.3-30B-A3B`); it was not run live because it needs an
80 GB-class GPU this machine does not have (see the README's "Built on Gnani.ai"
section for the vLLM/SGLang/HF Endpoint setup to run it for real).

| Probe | Result | Decision |
|---|---|---|
| TTS REST, 4 voice/language pairs (`Kaveri`/en-IN, `Nalini`/hi-IN, `Poorvi`/hi-en, `Poorvi`/en-IN) | All 4 returned HTTP 200 in 3.0–3.9 s, with WAV audio at `sample_rate=24000` as parsed from the header (118–185 KB each). `Poorvi` accepted `en-IN` and produced a similarly sized clip to `hi-en`, even though the voice catalog lists it only under `hi-en`. | Keep the documented pairing (`Kaveri` for `en-IN`, `Nalini` for `hi-IN`) as the default — it matches Gnani's own catalog — rather than the undocumented `Poorvi`-for-both shortcut. |
| TTS REST concurrency, 2 requests fired with `asyncio.gather` | The first returned 429, the second 200. | Confirms the docs' "only 1 active request at a time" limit is real for this key. The streaming `TtsStream` worker already serialises sentences one at a time; the REST retry in `gnani_tts.synthesize` (0.5 s, 1 s backoff) absorbs this for fillers and the REST fallback path. Two officers demoing at once will still occasionally see a filler delayed by one retry. |
| TTS WebSocket, one turn, 2 sentences | 40 `audio` chunks, 84,480 bytes total, none RIFF-prefixed (confirms raw `linear_pcm`, no header to strip) and every chunk an even byte length (so the odd-byte carry path in `_emit_pcm` was not exercised here, but stays in for files that do split a sample). Time to first audio 2.4 s from `begin_turn`, including the handshake. Stream ended in `ws` mode (no fallback triggered). | Keep `GNANI_TTS_MODE=ws`. The 2.4 s first-audio time is the WebSocket handshake plus Gnani's own synthesis latency for the first sentence; it is a cold path and the greeting already prewarms a filler clip 3 s in. |
| STT WebSocket, Hindi clip (the Hindi greeting re-synthesised at 16 kHz) | `connected` (with `config.partials_enabled: false`, confirming Gnani's own default has no partial transcripts), `speech_start`, then one `transcript` whose text closely matched the spoken greeting. 3 events total. | Confirms the no-partials design in `session.py`: the `final` transcript is the only text event, and it both shows the instant line and confirms barge-in. |
| STT WebSocket, English clip | Same 3-event shape; `transcript.text` was `"hello i am swasthya the control room voice analyst"` — a correct, lowercased, unpunctuated transcription of the greeting. | `format=transcribe` strips punctuation/casing as documented; `prepare_speech`/the LLM already handle lowercase input fine in later turns. |
| STT REST sanity check (English clip, `/stt/v3`) | HTTP 200, `transcript` matched the WebSocket run exactly. | REST and WebSocket STT agree; no surprises for the probe script's one-off sanity path. |
| LLM: Gemini tool-call round trip (`get_district_briefing` for Kota) | Tool call arrived after 1.68 s, carrying a Gemini 3 "thought signature" under `extra_content.google.thought_signature`. The follow-up call (tool result appended, `tool_choice: "none"`) returned a grounded answer ("there are currently 2 critical stock situations") with its first token after 1.53 s. | Confirms `ToolCallAccumulator.add` must preserve `extra_content` and `_run_tool_round` must send it back on the assistant message — both already implemented and exercised by `test_llm.py`'s accumulator test and manually confirmed live here. |
| LLM: Gemini `reasoning_effort` sweep (`none`, `minimal`, `low`) | `none` returned **HTTP 400 `INVALID_ARGUMENT`**. `minimal` and `low` both returned 200. | **Changed the default from `low` to `minimal`** (`backend/app/core/config.py`, `backend/.env.example`) — it is the lowest value this Gemini model actually accepts; `none` would make every voice turn fail outright. |

## Notes for later phases

- The one-active-request TTS limit means a production demo with two simultaneous voice
  users should expect an occasional extra ~0.5–1 s on one of them, not a hard failure —
  `gnani_tts.synthesize`'s retry and `TtsStream`'s own serialisation both already cover it.
- Evon v3.3's tool-calling behaviour is still unverified live (no GPU endpoint was
  available at probe time). The model card itself says tool use is "an active area of
  development," so the first real Evon endpoint should be run through
  `backend/evals/voice_eval.py` before claiming parity with Gemini's tool-calling
  reliability shown here.
